# Release decisions — writeup for sign-off

**Status:** three decisions block calling this app production-ready. None can be
resolved in code review alone; each needs the owner's call. Everything below is
verified against the current files (as of 10 Nov 2026). Nothing else was changed
to make this list shorter — the point is to name exactly what a signature on a
page cannot supply.

## 1. Release signing — release builds are signed with the *debug* key

**Evidence.** `android/app/build.gradle`:

```gradle
buildTypes {
    debug  { signingConfig signingConfigs.debug }
    release { signingConfig signingConfigs.debug }
}
```

and `signingConfigs.debug` points at `debug.keystore` with password "android".
That keystone is **intentionally committed** — it exists so CI doesn't rotate
signing keys per run, breaking in-place upgrades of sideloaded builds. It is a
debug key. It authenticates nothing.

**What's actually needed.** A private release keystore, generated by the owner,
stored outside the repo. Minimum viable path:

1. `keytool -genkey -v -keystore shos-release.jks -alias shos -keyalg RSA -keysize 2048 -validity 10000`
2. Move it somewhere the build can read it, plus `android/keystore.properties`
   (untracked) with `storeFile`, `storePassword`, `keyAlias`, `keyPassword`.
3. Add `signingConfigs.release { ... }` reading those properties; change only
   the release line to `signingConfig signingConfigs.release`.
4. Decide on Play Store vs. sideload-only distribution. The in-place-update
   problem already solved for debug builds applies identically to release.

**Risk not handled by this doc alone:** if a release build already shipped with
the debug key, it is already entangled with every Play Store upload channel the
app could use — the release key must be chosen *before* the first distribution.

## 2. CSP — the PWA ships no Content-Security-Policy

**Evidence.** `android/app/src/main/assets/public/index.html` (the built shell)
and `public/index.html` source contain **no** `Content-Security-Policy` meta
tag, and no `Content-Security-Policy` HTTP header exists on the web deployment
either. The app loads only self-hosted assets (fonts via @fontsource, no CDN)
so today there is nothing to exfiltrate to — but CSP is the belt that stops a
single compromised dependency from becoming one.

**What's actually needed.** Owner's choice of policy. The conservative starting
point that matches the app's self-hosted reality:

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; connect-src 'self'; font-src 'self'; object-src 'none';
base-uri 'none'; frame-ancestors 'none'
```

`style-src 'unsafe-inline'` is required because the codebase writes inline
`style={{}}` everywhere by design (no CSS files by design). Removing it is a
real design decision, not a config tweak.

**Questions for the owner.**
- Does the PWA deploy (web-alpha.yml) stay a supported installation target, or is
  it a demo surface only? CSP only affects the web build.
- Is `'unsafe-inline'` acceptable in `style-src`, or is a style nonce plan on the
  table?

## 3. Version accuracy — Android shows 1.0 while the app is 0.2.0

**Evidence.** `android/app/build.gradle`:

```gradle
versionCode 1
versionName "1.0"
```

`package.json` is `0.2.0`; Settings → About reads `__APP_VERSION__` from the
bundle, so the two disagree on every real install. A Play Store release with a
wrong version name is recoverable but embarrassing.

**Minimum decision.** Decide what `versionName` says: the app's own semver
(0.2.0, recommended — one number from About, one source of truth in package.json)
or a fresh Android-facing version (1.0). If the former, a two-line Gradle change
is all that's needed, plus a decision on `versionCode`.

## 4. What this means in practice

None of 1–3 blocks continued development. All three block calling anything a
**release**. Until the owner signs off on these, the honest thing to ship is a
debug build for evaluation, not a distributed release.
