### Methodological caveats — READ BEFORE TRUSTING ANY FINDING
- **Fact vs inference:** Each item is labelled OBSERVED (seen on screen / in console) or INFERRED (my interpretation). Anything not explicitly confirmed is marked ⚠️ needs confirmation.

🔴 BUG — Update banner never truly dismisses (owner-reported, reproduced + code-confirmed)
- **Symptom:** Banner "A new version is ready. Back up your data first, then refresh." reappears after refresh and after tapping ✕.
- **Root cause (definite):** The dismiss button writes `sessionStorage.setItem("shos-sw-update-dismissed", "1")` (`src/App.jsx:3319`), but all four guards read **`localStorage.getItem("shos-sw-update-dismissed")` and treat it as a timestamp** (`Date.now() - parseInt(d) < 86400000`) at `App.jsx:1483`, `:1505`, `:1538`, `:1579`. Storage areas differ (`sessionStorage` vs `localStorage`) AND value format differs (`"1"` vs epoch ms). So the flag can never satisfy the guard.
- **Why it shows at all:** Three independent triggers can set `swUpdateAvailable`: (1) SW `controllerchange` (`:1505`), (2) `version.json` SHA mismatch (`:1537`, deployed `buildSha: d75b648` vs baked `__BUILD_SHA__`), (3) GitHub release tag > `__APP_VERSION__` (`:1578`). Live check confirmed `version.json` from GitHub returns `channel: stable, version 0.2.0, buildSha d75b648`. If the deployed bundle's `__BUILD_SHA__` differs from that file, the banner fires permanently on every load — which is what we see.
- **Web-irrelevant action:** "Download APK" link shown on the web/PWA build (`App.jsx:3318`) — owner asks why a web user is offered an APK download; the web build is always most up to date, so the whole banner is questionable on web.
- **Reference:** `src/App.jsx:1478-1587` (three triggers), `:3297-3321` (banner UI), `:3319` (broken dismiss).

🟠 Inconsistent — top-bar icon set varies per module (see each tab below): Home shows 4 icons (search/profile/settings/exit); Encounter shows only Select + exit; Healthcare shows only exit. Owner: standardisation is an open BACKLOG 0b item.
