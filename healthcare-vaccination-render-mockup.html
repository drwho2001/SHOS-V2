Healthcare · Vaccinations — card render set

Vaccinations carries a dose series (1 of 2, 2 of 3…), per-dose next-due, provider, injection site (+ arm side), reason, symptom/reaction link, and clinic-visit linkage (visit owns the link via vaccinationsGivenIds). Every capturable form fact is represented on the card — nothing is invented for the card that the form cannot capture. Rendered in the STI/testing grammar on a 393dp device that shrinks to fit narrow panes.

States

Dot = action state: clinic accent (hc) = up to date, amber = next dose due, red = overdue, teal = revaccination / antibody check due. Summary is a store-once lead-word state line (COMPLETE / OVERDUE / DUE / REVACCINATION / SUGGESTED); chips never repeat the summary.

Legacy data import (no continuous provider)

User vaccinated for Hep B at occupational health, needs it again in 5 years, may have lost immunity / be at risk sexually and eligible — doses may not be at any one provider. Risk-profile eligibility suggestion

Based on sexual-health risk profile, the app can suggest vaccinations the user is eligible for but hasn't had — e.g. Hepatitis B, Mpox, HPV — even if no dose has ever been logged. Each suggestion carries a reason and links to guidance.

Render note: this is a design mockup. New features shown — serum antibody (titer) check, revaccination after ~5 years (risk-based only, per CDC), legacy/historical import without continuous provider, risk-profile eligibility suggestions, injection-site side marker — are acceptable additions to the form schema. The live vaccination module owns persistence, loading/empty states, native-dialog replacement, and amendments/modifications (BACKLOG 13). Those are wiring gaps, not card-design defects.
